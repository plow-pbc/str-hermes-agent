# Airbnb Operations Wiki — schema

Three categories, do not create more: `properties/` (one hub page per property),
`operations/` (one page per thing that works a certain way), and
`people/` (the standing cast — `people/key-people.md`, created on the first
person named in an ongoing role, opening with `type: Person`). `people/` is not
seeded: the deploy overwrites every file it ships, so a seeded copy would reset
it every release.

Operations page ids are `operations/<property-slug>-<topic>.md`, where the
slug is the filename of that property's hub under `properties/` — the hubs
are the list of properties; do not invent a slug that has no hub.

A hub's `## Operations` list is generated by `bin/build-hubs` from the `title:`
of every `operations/<hub-slug>-*.md`, on every nightly and every deploy. Do not
edit it by hand. Its prose is hand-authored and is kept.

So a page's `title:` must open with its hub's exact title and a space —
`Cedar Cabin parking and snowplow rules`, never `Cedar Cabin: parking` or
`Cedar Cabinet parking`. `build-hubs` refuses anything else rather than
publish a mangled label, and it derives every hub before it writes any, so one
mistitled page stops the deploy's rebuild of all of them until a human retitles
it.

## What belongs here

Durable operational facts — true next year, and a future guest will hit this.
Not every future guest: a quirk that only bites in winter, or only in one room,
is durable, it just isn't universal. "The kitchen island and toaster outlets
share one GFCI whose reset is behind the pantry door" is a fact. "a guest's
toaster didn't work on July 27" is an incident, and belongs only in `_raw/`.

When a conversation describes a one-off event, ask what it reveals about how the
property works.

### Writing a bullet

**One bullet per fact.** Before adding one, read the page and check whether it
already says this. If it does, fold the new detail into the bullet already
there. Appending by default is what produced seven ways of saying dogs need
advance notice: each batch looked like it was adding information, and the page
ended up with parallel copies that drift apart the moment one is corrected.

**When sources disagree, resolve it** — don't average them, don't take the most
generous reading. State what is reliably true, put the leftover uncertainty in
its own bullet, and say what separates them. A page an agent can read two ways
is worse than one that admits what it does not know.

**Mark uncertainty with the toolkit's own markers.** These are defined by
`llm-wiki/SKILL.md`, which generates these pages — this file does not get to
redefine them:

- `^[inferred]` — generalizing across sources, drawing an implication, or
  filling a gap.
- `^[ambiguous]` — sources disagree, or the source is vague.

What this repo adds is the consequence: an unmarked bullet is a promise an
agent may repeat to a guest verbatim. A marked one must be verified first, even
when the bullet itself explains the doubt.

### Worked examples — this is the bar

These are real, and they calibrate the threshold. Aim here.

**Write this** (durable, a future guest will hit it, in no Hostex field):

> - Do not tell guests to park on Cedar Cabin Rd. Street parking can block
>   emergency services and snowplow access.
> - The HOA may tow vehicles parked on the road.
> - The driveway reliably fits four vehicles. Anything beyond that needs host
>   approval for the specific booking.
> - A fifth car has fit by parking off to the side on the gravel; treat that as
>   a case-by-case approval, not capacity to advertise. ^[ambiguous]

The first three lines are quotable to a guest as they stand. The fourth is
marked because the sources behind it disagree on how many cars fit — the
resolution above it is what an agent quotes, and this records the exception
without promising it.

**Write this** (a quirk a guest will hit again):

> The kitchen island, toaster and coffee-maker outlets share one GFCI that trips
> under combined load. The reset is behind the pantry door, not in the breaker box.

**Do not write this** (an incident; the fact above is what it yielded):

> On 2026-07-27 a guest reported the kitchen outlets dead and tried the GFCI.

**Calibration:** a batch of 25 guest conversations should normally yield
**several facts captured**, not zero. Count facts, not pages: folding into an
existing bullet is the common case, so a healthy run often creates no new page
at all and a page count can't tell a good run from a silent one. Most individual
messages are logistics and pleasantries and produce nothing — that is expected —
but a whole batch producing nothing means the bar has drifted too high, not that
the property has no quirks. Extract the operating fact behind the exchange
rather than declining because the exchange itself was mundane.

## What gets written down

**Write what will be true for the next guest. Leave out what was true for one
stay.** One test, applied to facts, codes, and people alike.

**Codes and access.** Door codes, keypad and garage codes, where a key is kept,
which door is the entry fallback — write them, with the same specificity the
conversation had. Getting a guest into the property is the job; a page that
withholds the answer sends them to a human at 2am, which is the cost this wiki
exists to remove. The repo is private and stays private (see the README banner).
A code belonging to one stay fails the test — a temporary code for early entry,
a booking-window code, one the conversation shows failing or being replaced.
Write what the exchange taught about the *workflow* ("early entry needs a
host-issued temporary code") and leave the value out — a page is read months
later by a guest it was never about.

**People.** An ongoing role is a standing fact, and the most useful thing an
employee knows is who to call: the cleaning crew, the maintenance contact, the
neighbour with a key, the plumber. Write them down the first time they are
named — the role is what makes them durable, not a second mention, which no
single ingest turn could see anyway. Name and number, in `people/key-people.md`.
A departing guest's name, phone, or arrival date was true for one stay — it
stays in `_raw/`, which no page quotes. That applies to the worked
examples in this file too: this file is tracked in the code repo, so an
illustration must not carry the thing it is illustrating.

## Citing a source

Every operations page links to its property hub, and every page cites the
conversation it came from, following `wiki-ingest`'s source-inheritance rule —
the same deference the
uncertainty markers get above. That rule says the `_raw/` path is a staging
artifact and must never be the `sources:` value; the entry comes from the raw
file's own frontmatter. Ours carry `capture_source: hostex` and a `sources:`
link, so a citation is the Hostex conversation URL:

> ```yaml
> sources:
>   - https://hostex.io/app/conversations/<conversation-id>
> ```

The path was never a usable citation. `_raw/` is excluded from the code repo,
so a reader working from a checkout cannot open the file; and `wiki-ingest`
archives a conversation somewhere under `_raw/` once it has pages — it does not
settle on one layout, which is why `bin/ingest-all` walks the tree rather than
naming paths — so the path stops resolving even there. The URL is durable,
clickable, and names the conversation
rather than the file that happened to carry it.

`pages_produced` in `.manifest.json` is derived — `bin/ingest-all` writes it
from the pages' own `sources:` once the run is over, so the two cannot disagree.
Cite the conversation on the page and the field follows. Do not hand-reconcile
it.

**One copy, in frontmatter.** No `## Sources` block restating it: that is a
second copy nothing derives from the first, and the two drift the moment one is
edited alone. That holds when the page already exists, which is the case this
rule kept losing: a citation added to a page you are *updating* goes into that
page's `sources:` list, not the end of its body. Inserting into a mid-file YAML
list is the harder edit and appending to the body is the cheap one, so a run
that is mostly updates drifts that way under its own weight — a regeneration
did it 38 times in one night, leaving bare URLs indented under whatever bullet
happened to be last. A source URL appears in a page **only** in `sources:`.
Copy it verbatim from the raw file's frontmatter; the same run retyped 392 of
them as `tps://…`, which satisfies every check that joins on the conversation
id and resolves nowhere for a reader. **No digest either** — `.manifest.json` owns those. A page that
restated a digest held a third copy of the same fact, and because a digest is
unreadable the drift was invisible until a test caught it.
